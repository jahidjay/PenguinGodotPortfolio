# Art Pipeline — how to replace any sprite in MorutJan

Everything the game draws is a PNG in `assets/art/` plus one line in a `.tres`
that points at it. Nothing is hardcoded in a script. To change the art you
drop in a new PNG and, if the filename changed, repoint one line.

Current art is **placeholder**: generated by `tools/gen_placeholder_art.gd` so
the game has something on-spec to draw. Replacing it is the expected path.

---

## 0. The 60-second version

1. Draw a PNG at the size in the table below.
2. Save it over the existing file in `assets/art/...` (keep the name).
3. Open the project in Godot once, or run `godot --headless --path . --import`.
4. Run the game. Done — no code change, no `.tres` change.

Keeping the filename is the whole trick. If you want a different name, you
also edit the one `.tres` line listed in the table.

**Warning:** `tools/gen_placeholder_art.gd` **overwrites** the generated files.
Once you hand-draw something, either stop running that script or delete the
function that writes your file. There is a list of exactly what it writes in
§7.

## 1. The canvas and the rules that come from it

| Thing | Value | Why |
|---|---|---|
| Canvas | **360 × 640** px | `project.godot` `viewport_width/height` |
| Window | 720 × 1280 (2× integer) | `window_width_override` |
| Stretch | `canvas_items` | one art size, scaled by whole numbers |
| Filter | **Nearest** (`default_texture_filter=0`) | pixels stay pixels; no blur |

Consequences you cannot ignore:

- **Draw at 1×, not 2×.** A 48 px plane is 48 px in the file. The window
  scales it. A 96 px plane will be twice as big in game as the one it replaced.
- **Even width and height.** Sprites are drawn centred and snapped to whole
  pixels (`Run._draw_centred`); an odd size lands on a half pixel and the
  outline goes soft. The generator's check rejects odd frames outright.
- **Transparent background**, not a matte colour.
- **No anti-aliasing and no soft shadows.** With Nearest filtering, a 50%
  alpha edge pixel reads as a dirty fringe, not as smoothing.

## 2. Where every sprite lives

`data/art/run_visuals_1941.tres` is the one resource that holds the player-side
art. Open it in the Godot inspector (or a text editor — it is a text file) and
you will see every field below.

### 2.1 Player planes

| | |
|---|---|
| Files | `assets/art/players/char_<kit>_p<N>_48x48.png` |
| Kits | `lancer`, `leech`, `sentry`, `breaker` |
| N | 1–4, the player slot, which sets the outline colour |
| Size | **48 × 48** (art bible §8.3 character tier), 16 colours max |
| Pointed at by | `run_visuals_1941.tres` → `plane_sprites`, a flat array of 16 |
| Indexing | `type * 4 + slot`. P1 flies type 0, P2 type 1, and so on |

There are 16 files because each of the four airframes exists in each of the
four player colours. If you only care about solo play, the four you need are
`char_lancer_p1`, `char_leech_p2`, `char_sentry_p3`, `char_breaker_p4`.

The plane's **nose must point up** and its visual centre must be the centre of
the frame — that point is where bullets spawn from and where the hitbox is.

### 2.2 The hitbox dot

| | |
|---|---|
| Files | `assets/art/players/icon_hitbox_p<N>_12.png` |
| Size | 12 × 12, 6 colours |
| Pointed at by | `hitbox_sprites` (4 entries, one per slot) |

This one has a hard rule (art bible §4.4): **it is always visible, it never
blinks, and it draws over everything except enemy bullets.** The actual
collision circle is ~2 px; the ring is a reading aid. Each slot uses a
different ring *pattern*, not just a different colour, because P3 and P4 have
the same luma and a colourblind player needs the pattern.

### 2.3 Drones

| | |
|---|---|
| File | `assets/art/players/drone_pod_p1_12.png` |
| Size | 12 × 12, 6 colours |
| Pointed at by | `drone_sprite` (a single texture today) |

### 2.4 The player's shot

| | |
|---|---|
| File | `assets/art/shots_fx/shot_streak_10x18.png` |
| Size | ≤ 10 × 18, **4 colours**, and **no dark outline** |
| Pointed at by | `shot_sprite` |

One sprite serves every player bullet — the Lancer fan, the Leech focus pair,
the Sentry cannon shell, the Breaker slug and bolt, and drone fire. It is
tinted per shooter so four players can tell their shots apart.

§4.4 is strict here: **a player shot must never look like an enemy bullet.**
Keep it warm (the player palette is `pal_players.gpl`) and keep the dark
outline off — outlines are reserved for enemies and enemy bullets.

### 2.5 Enemy bullets — the atlas

| | |
|---|---|
| File | `assets/art/shots_fx/bullet_atlas_64x16.png` |
| Layout | **one row of four 16 × 16 cells**, left to right |
| Cells | `ORB`, `RICE`, `NEEDLE`, `RING` (`BulletRules.Shape` order) |
| Pointed at by | `bullet_atlas`, with `bullet_atlas_cells = 4` |
| Tint | `bullet_colors` — a `PackedColorArray`, one per shape |

This is the single highest-impact file in the game: it re-skins every enemy
bullet at once. It is drawn through one MultiMesh with
`src/gameplay/bullets/shaders/bullet_atlas.gdshader`, which picks the cell from
`INSTANCE_CUSTOM.x`, so **2,000 bullets of four shapes still cost one draw
call**. Do not turn these into individual sprites; it is what keeps the frame
rate.

Two rules worth stating plainly:

- **Draw the cells white on transparent.** The colour comes from
  `bullet_colors`. Painting the hue into the PNG takes it out of data.
- **The fill hue is locked to 225–265° (indigo/blue) in every era** (§4.3).
  Cyan, teal, violet-pink and white are banned as bullet fills, so a player's
  colour-reading skill carries from 1941 to 2100. The outline is always 1 px
  of Ink.

Setting `bullet_atlas` to null is legal: the game then draws plain tinted
quads and plays identically.

### 2.6 Enemies

Each enemy owns its own art, in its own resource:

```
data/enemies/1941/scout.tres          sprite = assets/art/enemies/1941/enemy_popcorn_scout_1941_24.png
data/enemies/1941/prop_fighter.tres   ... enemy_popcorn_prop_1941_26.png
data/enemies/1941/flak_gunner.tres    ... enemy_mid_flakgunner_1941_48.png
data/enemies/1941/heavy_bomber.tres   ... enemy_large_bomber_1941_96.png
                                      plating_sprite = ..._96_plate.png
data/enemies/1941/boss_fortress.tres  ... boss_fortress_hull_216.png
```

Size tiers (§8.3), by `size_class`:

| Class | Max frame | Colours | Examples |
|---|---|---|---|
| SMALL (popcorn) | 27 × 27 | 8 | scout, prop fighter |
| MEDIUM | 48 × 48 | 12 | flak gunner |
| LARGE | 96 × 96 | 16 | heavy bomber |
| BOSS | 216 × 216 | 24 | the Flying Fortress |

Enemies face **down** (they are flying at the player). Every enemy carries a
**1 px Ink outline** — that outline is what separates "enemy" from
"background" at a glance, and the player's plane deliberately does not have one.

`plating_sprite` is an **overlay drawn on top of the body** while the enemy is
armoured, not a recolour, so the silhouette underneath still reads (§5.7).

### 2.7 Score items

| | |
|---|---|
| Files | `assets/art/items/item_{pod_16,chain_14,medal_14,1up_16,gem_10}.png` |
| Pointed at by | `item_sprites`, in `ItemField.Kind` order: POD, CHAIN, MEDAL, 1UP, GEM |

Two rules: items are **cream and warm, never the locked bullet hue** (an item
must never be mistaken for a bullet), and each kind carries a **different
glyph**, so the kind reads without colour.

### 2.8 The scrolling world

| | |
|---|---|
| Files | `assets/art/env/1941/strips/env_strip_{far,mid}_1941_*.png` |
| Width | **376 px** (360 + 8 px overscan each side, for screen shake) |
| Height | anything, but it must **tile seamlessly top to bottom** |
| Pointed at by | `strip_far`, `strip_mid` |
| Speed | `far_scroll_per_tick` (0.25), `mid_scroll_per_tick` (0.6) |

This is a **top-down** game: the far strip is distant ground, the mid strip is
closer ground and props. Neither is sky. Far scrolls slower than mid — that
difference *is* the parallax.

One constraint that is easy to miss: **keep the central ~120 px quiet.** That
is the lane the player flies in, and busy art there hides bullets.

## 3. Adding a sprite that does not exist yet

Three steps, in the Godot editor:

1. Put the PNG in the right folder under `assets/art/`.
2. Open `data/art/run_visuals_1941.tres` (or the enemy's `.tres`) in the
   inspector and drag the texture into the field.
3. Save.

By hand in a text editor, a `.tres` needs two lines — an `ext_resource` header
entry and the assignment — and `load_steps` bumped by one:

```
[gd_resource type="Resource" script_class="RunVisuals" load_steps=33 format=3]
...
[ext_resource type="Texture2D" path="res://assets/art/players/my_plane.png" id="mine"]
...
shot_sprite = ExtResource("mine")
```

## 4. Palettes

`assets/art/palettes/` holds seven palettes as both `.gpl` (Aseprite, GIMP,
Krita: **Palette → Load**) and `.hex` (plain text, for anything else):

| File | What it is for |
|---|---|
| `pal_global` | Ink, Cream, Tracer Orange, Gold — shared by every era |
| `pal_players` | the four slot colours and the player-shot ramp |
| `pal_ui` | HUD and menus |
| `pal_1941`, `pal_1970s`, `pal_2030s`, `pal_2100` | one per era |

Staying on palette is what makes four eras of art look like one game. The
colour caps in §2 are per sprite, not per palette.

---

## 5. What happens if you do nothing

Every sprite field is allowed to be null. The run scene draws a primitive
instead — a triangle for a plane, a polygon for an enemy, a tinted quad for a
bullet. The game is fully playable with an empty `assets/art/`. So you can
replace art one file at a time and never have a broken build.

## 6. Checking your work

```bash
# Re-import after adding or replacing files
godot --headless --path . --import

# Play it (straight into the run, skipping the title)
godot --path . res://src/gameplay/run/run.tscn
```

What to look at, in order:

1. **Silhouette.** Squint. Can you tell a scout from a prop fighter?
2. **The bullet rule.** Bullets draw over everything they could be confused
   with, and the hitbox dot draws over everything except bullets. If your new
   art ever hides a bullet, the art is wrong, not the code.
3. **The quiet lane.** Fly down the middle. Can you still see every bullet?
4. **Both at 1× and 2×.** Launch at 360 × 640 and at 720 × 1280.

## 7. The placeholder generator (and how to stop it)

`tools/gen_placeholder_art.gd` writes **42 files** and fails the run if any of
them breaks its §8.3 size tier or colour cap:

```bash
godot --headless --path . --script res://tools/gen_placeholder_art.gd
```

It writes into `assets/art/`: `players/` (16 planes, 4 hitboxes, 4 drone pods),
`enemies/1941/` (5), `bosses/` (4), `shots_fx/` (player shot + bullet atlas),
`items/` (5) and `env/1941/strips/` (2).

**It overwrites.** The moment you hand-draw one of those files, delete the
`_save(...)` line that writes it, or move your art to a new filename and
repoint the `.tres`. The second is safer.

`tools/pixel_canvas.gd` is the little drawing library behind it (`rect`,
`ellipse`, `capsule`, `trapezoid`, `outline`, `mirror_left_to_right`,
`dither_rect`, plus `colour_count()` and `bounds()` for the checks). It is
also the fastest way to prototype a shape before drawing it properly.

## 8. Not built yet

Be aware these do not exist, so there is nothing to replace:

- **Animation frames.** Every sprite is one static frame. No banking, no prop
  blur, no death animation.
- **Explosion and impact VFX** (GDD 25). Hits currently show nothing.
- **HUD plates** (GDD 7/20). The on-screen text is a debug readout.
- **Damage states** on enemies and bosses.
- **Eras 2–4.** Only 1941 art exists; the palettes for the others are ready.
- **Boss parts.** The Fortress is drawn as one body; its turret, engine and
  core sprites are generated but unused until Boss (14) lands.
